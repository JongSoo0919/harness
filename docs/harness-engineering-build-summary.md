# 하네스 엔지니어링 구축 정리

이 문서는 AI 에이전트를 활용한 기획, 개발, 테스트, 운영 점검, 문서화 흐름을 안정적으로 만들기 위해 설계한 범용 하네스 엔지니어링 작업을 정리한 문서다. 목적은 단순히 “AI에게 일을 시켰다”가 아니라, AI가 같은 규칙과 같은 안전망 안에서 반복적으로 일할 수 있도록 실행 구조를 설계했다는 점을 설명하는 것이다.

하네스 엔지니어링은 AI 에이전트를 둘러싼 실행 환경, 입력 규격, 단계별 승인 구조, 검증 gate, 실패 학습 루프, 문서화 체계를 설계하는 작업이다. 즉, AI의 답변 능력 자체에만 의존하지 않고, AI가 작업을 수행하는 방식을 시스템화하는 접근이다.

## 왜 필요했는가

AI 에이전트에게 자연어로 “이 기능 개발해줘”, “운영 개선해줘”, “로그 추가해줘”처럼 요청하면 매번 결과의 품질이 달라질 수 있다. 어떤 때는 요구사항을 충분히 물어보지 않고 바로 구현하고, 어떤 때는 테스트를 생략하고, 어떤 때는 문서를 갱신하지 않거나, 어떤 때는 위험한 변경을 사용자의 승인 없이 진행할 가능성이 있다.

특히 백엔드, 프론트엔드, DB, 운영 문서, 권한 정책, 예외 처리, 배포 스크립트가 모두 연결된 프로젝트에서는 단순 코드 생성보다 “일하는 방식”이 더 중요하다. 한 API를 추가하더라도 권한 정책이 빠지면 보안 문제가 되고, 예외 응답 규격이 다르면 프론트와 연동이 깨질 수 있으며, 운영 로그가 부족하면 장애가 났을 때 원인을 추적하기 어렵다.

따라서 AI가 매번 다른 방식으로 일하지 않도록, 입력부터 기획, 개발, 테스트, 운영 점검, 문서화, 공유까지의 흐름을 하네스로 묶었다.

## 구축한 하네스의 핵심 구조

### 1. 자연어 요청을 Input Schema로 규격화

가장 먼저 자연어 요청을 그대로 실행하지 않고, Input Schema로 규격화하는 구조를 만들었다. 사용자의 요청은 처음에는 모호할 수 있다. 예를 들어 “미들웨어 헬스 체크 추가해줘”라는 요청만으로는 어떤 미들웨어를 대상으로 할지, 읽기 기반인지 쓰기 기반인지, 운영 노출 범위는 어디까지인지, 프론트 화면이 필요한지, 테스트 기준은 무엇인지가 명확하지 않다.

그래서 `input.yaml` 형태의 입력 계약을 정의했다. 작업 제목, 작업 유형, 변경 범위, 제외 범위, 위험 태그, 승인 필요 여부, 검증 기준, 문서화 필요 여부, git 브랜치 기준 등을 같은 형식으로 기록하도록 했다. 이 구조를 통해 AI는 질문을 통해 부족한 필드를 채워야 하고, 사용자는 AI가 이해한 내용을 확인한 뒤 개발을 승인할 수 있다.

이 작업의 의미는 입력 품질을 일정 수준 이상으로 끌어올리는 데 있다. 자연어 요청은 사람마다, 상황마다 달라지지만 Input Schema는 고정되어 있다. 즉, 질문은 자유롭게 시작하더라도 개발에 들어가기 전에는 항상 같은 규격의 작업 정의로 수렴하게 만든 것이다.

### 2. 작업 단계를 역할별로 분리

두 번째로 작업 단계를 분리했다. 전체 흐름은 `plan -> dev -> test -> ops -> document -> share`로 나누었다. 각각의 단계는 역할이 다르다. `plan`은 요구사항을 확정하고, `dev`는 최소 변경으로 구현하고, `test`는 검증하고, `ops`는 운영 리스크를 확인하고, `document`는 문서와 위키 초안을 정리하고, `share`는 커밋과 PR 공유를 준비한다.

이 단계 분리는 AI가 한 번에 모든 일을 섞어서 처리하지 않도록 만드는 장치다. 기획이 끝나지 않았는데 개발하지 않고, 테스트가 실패했는데 공유하지 않고, 운영 리스크가 남아 있는데 PR로 넘기지 않도록 흐름을 강제한다.

### 3. 단계별 산출물 규격 정의

세 번째로 각 단계별 산출물 규격을 만들었다. 전체 작업은 `docs/work/YYYY-MM-DD-task/` 아래에 `input.yaml`, `01-plan.md`, `02-dev-result.md`, `03-test-result.md`, `04-ops-check.md`, `05-summary.md`, `harness.json`을 남기도록 했다.

산출물을 남기는 이유는 두 가지다. 첫째, AI가 어떤 판단으로 작업했는지 사람이 추적할 수 있다. 둘째, 다음 단계의 AI가 이전 단계의 산출물을 기준으로 이어서 작업할 수 있다. 예를 들어 테스트 단계는 개발 결과 문서를 보고 검증 범위를 잡고, 운영 점검 단계는 테스트 결과와 변경 파일을 보고 운영 리스크를 판단한다.

### 4. Gate 기반 품질과 안전 검증

네 번째로 gate를 만들었다. gate는 다음 단계로 넘어가기 전에 반드시 통과해야 하는 검사다. 예를 들어 secret gate는 `.env`, key, token, password 같은 민감정보가 변경분에 포함되면 즉시 중단한다. output gate는 필요한 산출물이 모두 있는지 확인하고, output quality gate는 산출물 안에 목표, 범위, 대안, 테스트 결과, 운영 영향 같은 필수 판단 항목이 채워졌는지 확인한다. 프로젝트에 따라 권한, API contract, migration, E2E 테스트 같은 gate를 추가할 수 있다.

이 gate의 의미는 AI의 자율성을 막는 것이 아니라, 최소 품질선을 만드는 것이다. AI가 빠르게 작업하더라도 secret을 커밋하거나, 테스트 없이 공유하거나, 문서를 남기지 않고 끝내는 일은 gate에서 막힌다. 즉, 사람이 매번 기억해서 체크해야 하는 항목을 실행 가능한 규칙으로 옮긴 것이다.

### 5. 사람 승인 기반의 의사결정 구조

다섯 번째로 승인 구조를 만들었다. 계획 승인 전에는 개발로 넘어가지 않고, PR/push/외부 공유 전에는 사용자 승인이 필요하도록 했다. 또한 stage gate가 차단되었을 때는 단순히 실패로 끝나는 것이 아니라, 왜 막혔는지, 어떤 대안이 있는지, 사용자가 강제로 진행하려면 어떤 리스크를 승인해야 하는지 기록하도록 했다.

이 구조는 Human-in-the-loop를 명확히 하기 위한 것이다. AI가 판단할 수 있는 영역과 사람이 최종 결정해야 하는 영역을 분리했다. 특히 destructive 작업, secret 변경, 최종 PR 승인, wiki 승격은 자동화하지 않고 사람의 명시적 승인을 요구하도록 했다.

### 6. 실행 로그와 결정 로그 기록

여섯 번째로 실행 로그를 남겼다. `.harness/runs/` 아래에 `run.json`, `commands.log`, `gates.log`, `decisions.md`, `errors.log`를 남기도록 했다. 어떤 명령을 실행했는지, 어떤 gate가 실패했는지, 어떤 결정을 했는지, 에러의 원인이 무엇인지 기록한다.

이 로그는 장애 추적과 유사한 역할을 한다. AI 작업도 결국 하나의 실행 흐름이기 때문에, 실패했을 때 “왜 그렇게 판단했는가”를 추적할 수 있어야 한다. 실행 로그가 있으면 다음 에이전트나 사람이 같은 맥락을 다시 추측하지 않고 이어받을 수 있다.

### 7. 반복 실수를 줄이는 실패 학습 루프

일곱 번째로 실패 학습 루프를 만들었다. 에러가 발생했을 때 단순히 고치는 것으로 끝내지 않고, 그 원인이 LLM의 잘못된 추정이었는지 확인하도록 했다. 만약 AI가 문서를 읽지 않고 추정했거나, 현재 파일 내용을 확인하지 않고 패치했거나, stage gate의 의미를 잘못 이해했다면 그 내용을 `errors.log`에 기록하고, 다시 같은 실수를 하지 않도록 관련 `SKILL.md`나 reference 문서를 보강한다.

이 구조의 의미는 “실패를 재사용 가능한 규칙으로 바꾸는 것”이다. 일반적인 AI 사용은 실패가 대화 안에서만 사라지지만, 하네스에서는 실패를 규약으로 다시 흡수한다. 시간이 지날수록 프로젝트의 작업 방식이 단단해지는 구조다.

### 8. Wiki 초안 추출과 수동 승격

여덟 번째로 wiki 초안 추출과 수동 승격 구조를 만들었다. 작업 산출물에서 운영, 개발, 온보딩에 재사용할 수 있는 내용을 `docs/wiki/drafts/`로 추출한다. 단, 초안은 최종 wiki가 아니며 사람이 검토한 뒤에만 `docs/wiki/operation`, `docs/wiki/development`, `docs/wiki/onboarding`, `docs/wiki/lessons`로 승격한다.

이 구조는 개발 작업 중 생긴 지식을 조직 지식으로 전환하기 위한 것이다. 운영 리스크, 권한 정책, 테스트 기준, 장애 추적 기준 같은 내용은 한 번의 작업에서 끝나면 안 된다. 새로 들어온 사람이나 다음 AI 에이전트가 같은 기준을 볼 수 있어야 한다. 다만 자동 승격은 위험하므로 최종 wiki 반영은 사람이 승인하도록 했다.

## 실제로 밟은 설계 과정

### 1. 복합 프로젝트에서 반복적으로 발생하는 문제 파악

처음에는 실제 업무 프로젝트를 분석하면서 AI 에이전트가 놓치기 쉬운 지점을 확인했다. 백엔드, 프론트엔드, DB, 문서, 운영 스크립트가 함께 있는 구조에서는 한 파일만 고쳐서는 작업이 끝나지 않는다. API 변경은 프론트 호출 방식, 예외 응답, 권한 정책, 로그, 문서와 연결되고, 운영 기능은 health check, profile, scheduler, 외부 연동, 배포 방식과 연결된다.

이 과정에서 AI가 단순히 코드만 생성하면 운영 추적성, 권한 누락, 문서 불일치, 테스트 누락 같은 문제가 생길 수 있다는 점을 확인했다.

### 2. 운영 리스크를 먼저 개선

그 다음 운영 리스크를 먼저 보강했다. 로그가 부족하면 장애 추적이 어렵기 때문에 requestId/traceId 기반 로그가 필요하다는 점을 정리했다. 예외 처리는 개별 try-catch보다 공통 예외 처리 구조가 더 안정적이고, 권한 처리는 API를 추가할 때 명시적인 정책 선언이 있어야 안전하다는 점을 기준으로 삼았다.

이 단계에서 얻은 결론은 “AI에게 개발을 맡기더라도 운영 규칙, 예외 처리 규칙, 권한 규칙을 항상 먼저 읽게 해야 한다”는 것이었다.

### 3. AI가 읽고 따를 개발 지침을 구성

이 필요성을 바탕으로 `AGENTS.md`와 `.Codex/skills/*` 구조를 만들었다. 초기에는 단순히 기획, 개발, 테스트, 운영, 문서화, 공유 단계로 나누는 개발 흐름에 가까웠다.

하지만 단순한 순서만으로는 충분하지 않았다. 각 단계가 어떤 입력을 받아야 하는지, 어떤 산출물을 남겨야 하는지, 어떤 조건에서 다음 단계로 넘어갈 수 있는지가 필요했다.

### 4. 개발 흐름을 하네스 엔지니어링 구조로 확장

이후 이것을 진짜 하네스 엔지니어링에 가깝게 만들기 위해 입력 표준화, 단계별 산출물, stage gate, safety gate, 실행 로그, 실패 학습 루프, wiki 초안 추출, 수동 승격 기준을 추가했다. 단순한 작업 순서가 아니라, AI의 행동을 제어하고 검증하고 학습시키는 실행 구조로 확장한 것이다.

이 단계에서 하네스는 “프롬프트 모음”이 아니라 “AI 작업 실행 환경”이 되었다. 사용자의 자연어 요청은 `input.yaml`로 수렴하고, 각 단계는 산출물을 남기며, gate는 다음 단계 진입 조건을 확인하고, 실패는 다시 규칙으로 반영된다.

### 5. 특정 프로젝트 의존성을 제거하고 범용화

그 다음 특정 프로젝트에 종속된 내용과 범용 하네스 내용을 분리했다. 프로젝트 전용 업무 지식, 내부 주소, 특정 기능명, 특정 도메인 문서를 제거하고, 어느 프로젝트에 클론해도 쓸 수 있는 구조로 정리했다.

skill 이름도 범용적으로 `plan`, `dev`, `test`, `ops`, `document`, `share`, `flow`로 정리했다. 이를 통해 하네스는 특정 서비스 개발에만 묶이지 않고 신규 제품 기획, 유지보수, 운영 개선, 장애 대응, 문서화 작업에도 사용할 수 있는 형태가 되었다.

### 6. Stage gate와 최종 산출물 gate 분리

범용화 과정에서 stage gate와 최종 산출물 gate를 분리했다. 이전에는 `--work-dir`만 지정해도 전체 산출물을 강제하는 문제가 있었는데, 실제로는 개발 단계 진입 가능 여부만 확인하고 싶은 경우가 있다.

그래서 stage gate는 단계 진입 조건만 확인하고, 최종 산출물 검증은 `--require-work-output`, `share`, `pr` 단계에서 수행하도록 정리했다. 이 분리는 하네스를 더 실용적으로 만들었다. 진행 중인 작업에는 진행 중인 작업에 맞는 gate를 적용하고, 공유 직전에는 전체 산출물 품질을 강하게 확인할 수 있기 때문이다.

### 7. Wiki와 lesson 산출물의 부작용 제거

wiki 초안 추출 경로를 `--wiki-dir`로 분리할 수 있게 했다. 테스트나 임시 검증을 할 때 실제 `docs/wiki/drafts`를 더럽히지 않기 위해서다.

또한 lesson 수집도 에러가 없을 때 빈 문서를 만들지 않도록 했고, 기존 파일의 timestamp만 바뀌는 불필요한 diff가 생기지 않도록 보강했다. 이는 하네스 자체가 작업트리를 불필요하게 오염시키지 않도록 하기 위한 개선이다.

### 8. 대상 프로젝트 루트 기준 명시

마지막으로 하네스가 적용될 대상 프로젝트의 루트 기준을 명시하도록 했다. 복합 프로젝트에서는 백엔드, 프론트엔드, DB, docs, scripts가 한 루트 안에 있을 수 있으므로, 특정 하위 프로젝트만 보고 판단하면 안 된다.

따라서 하네스를 도입할 때는 대상 프로젝트의 루트와 주요 디렉터리를 명시하고, AI가 코드, 문서, DB, 실행 스크립트의 영향을 함께 판단하도록 해야 한다.

## 이 작업의 의미

이 작업의 핵심은 AI를 단순 코드 생성 도구로 쓰지 않고, 팀의 개발 프로세스 안에 넣기 위한 실행 구조를 설계했다는 점이다.

Input Schema는 사용자의 자연어 요청을 같은 규격의 작업 정의로 바꾼다. 덕분에 AI가 매번 다른 기준으로 이해하지 않고, 목표, 범위, 리스크, 검증 기준을 확인한 뒤 작업한다. 이는 요구사항 품질을 안정화하는 역할을 한다.

단계별 skill은 AI의 역할을 분리한다. 기획 AI는 질문과 대안 제시에 집중하고, 개발 AI는 최소 변경과 컨벤션 준수에 집중하고, 테스트 AI는 검증에 집중하고, 운영 AI는 장애 추적과 배포 리스크에 집중한다. 하나의 프롬프트에 모든 역할을 섞는 것보다 책임이 명확해진다.

gate는 품질과 안전의 최소선을 만든다. secret, 산출물, 문서, stage 상태를 자동으로 점검하므로, 사람이 실수로 빼먹기 쉬운 항목을 반복적으로 확인할 수 있다. 특히 secret 커밋, 승인 없는 PR/push, 승인 없는 destructive 작업 같은 위험은 override 불가 항목으로 둬서 강하게 차단했다.

실행 로그와 산출물은 추적 가능성을 만든다. 어떤 명령을 실행했고, 어떤 판단을 했고, 어떤 gate가 실패했는지 남기기 때문에, 나중에 사람이 검토하거나 다른 AI가 이어받을 때 맥락 손실이 줄어든다.

실패 학습 루프는 AI의 반복 실수를 줄인다. 에러를 단순히 고치는 데서 끝내지 않고, 그 원인이 잘못된 추정이었다면 규칙으로 다시 반영한다. 이는 프로젝트를 진행할수록 하네스가 점점 프로젝트에 맞게 강화되는 구조다.

wiki 초안 추출은 개발 중 생긴 지식을 조직 지식으로 전환한다. 작업 산출물에서 운영 정책, 개발 규칙, 온보딩 지식을 분리해 초안으로 만들고, 사람이 검토한 뒤 확정 wiki로 승격한다. 이는 신규 합류자나 다음 작업자가 같은 시행착오를 반복하지 않게 하는 장치다.

## 면접에서 설명할 수 있는 방식

이 작업은 “AI를 활용해 개발했습니다”가 아니라 “AI가 안정적으로 개발할 수 있는 하네스 구조를 설계했습니다”라고 설명할 수 있다.

예를 들어 다음처럼 설명할 수 있다.

“처음에는 AI에게 자연어로 기능을 요청하면 결과 품질이 들쭉날쭉했습니다. 그래서 자연어 요청을 바로 구현하지 않고, 먼저 Input Schema로 변환하도록 했습니다. 목표, 범위, 리스크, 검증 기준, 문서화 필요 여부를 같은 형식으로 채우게 만들었고, 불명확한 부분은 AI가 질문하도록 했습니다. 이를 통해 개발 전 요구사항의 품질을 일정 수준 이상으로 유지했습니다.”

또는 다음처럼 설명할 수 있다.

“작업 흐름을 plan, dev, test, ops, document, share 단계로 나누고, 각 단계마다 산출물과 gate를 두었습니다. 테스트가 실패하면 개발 단계로 돌아가고, 운영 리스크가 남아 있으면 개발 또는 문서화 단계로 돌아가게 했습니다. PR이나 push는 사용자 승인이 있어야만 가능하게 했고, secret 같은 위험은 gate에서 차단했습니다.”

운영 관점에서는 다음처럼 설명할 수 있다.

“AI 작업도 운영 시스템처럼 추적 가능해야 한다고 보고, 실행 로그와 결정 로그를 남겼습니다. 어떤 명령을 실행했는지, 어떤 판단을 했는지, 어떤 에러가 발생했는지를 `.harness/runs`에 기록했습니다. 에러가 AI의 잘못된 추정에서 발생하면 그 내용을 다시 skill 문서나 reference 규칙에 반영해 같은 실수를 줄이는 루프를 만들었습니다.”

조직 지식 관점에서는 다음처럼 설명할 수 있다.

“작업 결과가 대화 안에서만 사라지지 않도록, 산출물에서 운영/개발/온보딩 wiki 초안을 추출하도록 했습니다. 다만 자동 승격은 위험하므로 사람이 검토한 문서만 최종 wiki로 승격하게 했습니다. 이를 통해 AI 작업 결과를 팀의 재사용 가능한 지식으로 전환할 수 있게 했습니다.”

## 결과적으로 만든 것

최종적으로 만든 것은 단순한 프롬프트 모음이 아니다. 입력 규격, 단계별 역할, 산출물 계약, gate, 실행 로그, 실패 학습, wiki 승격 정책이 연결된 AI 작업 실행 체계다.

이 구조를 통해 AI 에이전트는 프로젝트의 개발 규칙을 매번 새로 추측하지 않고, 정해진 문서와 gate 안에서 움직인다. 사람은 AI가 무엇을 했는지 추적할 수 있고, 위험한 작업은 승인 전 차단할 수 있으며, 반복되는 실수는 규칙으로 다시 흡수할 수 있다.

즉, 하네스 엔지니어링의 핵심은 AI에게 더 긴 프롬프트를 주는 것이 아니라, AI가 일하는 환경 자체를 설계하는 것이다. 이번 작업은 특정 프로젝트에서 발견한 문제를 출발점으로 삼되, 최종적으로는 어디에나 적용할 수 있는 범용 하네스로 정리한 과정이다.

## 한계와 다음 단계

현재 하네스는 강한 개발 규칙과 gate를 제공하지만, 모든 것을 자동으로 보장하지는 않는다. 예를 들어 사용자가 명시적으로 승인한 위험한 선택은 문서화할 수 있지만, 그 선택 자체가 항상 옳은지는 사람이 판단해야 한다. wiki 승격도 자동화하지 않고 사람이 최종 검토하도록 남겨두었다.

다음 단계로는 프로젝트별 gate를 더 정교하게 만들 수 있다. 예를 들어 DB migration 검증, 프론트 E2E 테스트, API contract 테스트, 운영 health check 검증, PR 템플릿 자동 점검 등을 추가할 수 있다. 또한 반복 실패에서 생성된 lesson을 주기적으로 검토해 확정 wiki나 skill 규칙으로 승격하는 운영 절차를 만들 수 있다.

이 방향으로 발전시키면 하네스는 단순한 AI 작업 보조 도구가 아니라, 팀의 개발 표준과 운영 지식을 지속적으로 강화하는 실행 기반이 될 수 있다.
